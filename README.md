# Operation Golden Keyboard - Backend Documentation

## Authentication Schemes Comparison

| Authentication Scheme | What is sent with every request | Expiry | Server State Storage | Verification Method | Advantages | Limitations |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **No Auth** | None | N/A | None | No verification | Fast, public access | Zero security |
| **Basic Auth** | `Authorization: Basic <base64(user:pass)>` | Never (unless pass changes) | Stateless (DB lookup per request) | Decodes Base64, checks credentials against DB | Simple standard | Sends password every time; unsafe without HTTPS |
| **Session Auth** | `Cookie: sessionid=<session_key>` | Configurable duration | Stateful (Stored in DB/Redis) | Server queries session table using cookie key | Built-in CSRF protection; easy to revoke | Scalability overhead across distributed servers |
| **Token Auth** | `Authorization: Token <token_key>` | Persistent (until deleted) | Stateful (Stored in `authtoken_token` table) | Server matches token string against DB user | Simple, persistent API access | Perpetual risk if leaked; requires DB lookup per request |
| **JWT Auth** | `Authorization: Bearer <access_token>` | Short-lived (e.g. 5 min) + Refresh token | Stateless (Token is self-contained) | Server verifies cryptographic signature using `SECRET_KEY` | Zero DB queries, high performance, scalable | Cannot revoke immediately without custom blacklisting |

## JWT Architecture & Anatomy

JWTs consist of three Base64URL-encoded parts joined by dots (`.`): `Header.Payload.Signature`

### Example Decoded JWT

#### 1. Header
```json
{
  "alg": "HS256",
  "typ": "JWT"
}

#### 2. Payload
```json
{
  "token_type": "access",
  "exp": 1728000000,
  "jti": "a1b2c3d4e5f6",
  "user_id": 1
}

#### 3. Signature
Generated by combining the header, payload, and server secret key using HMAC SHA-256:
`HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), SECRET_KEY)`

## Base64 Encoding vs. Encryption

* **Base64 Encoding:** A two-way data transformation scheme that converts binary data or strings into ASCII text. It provides **zero security** and is completely reversible without a key. Its purpose is safe data transmission, not protection.
* **Encryption (e.g., AES, RSA):** A security mechanism that obfuscates data using a cryptographic key. It ensures **confidentiality**—data cannot be decrypted or read without access to the corresponding decryption key.
